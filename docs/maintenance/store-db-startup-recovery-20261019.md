# Store 앱 DB 초기화 오류 점검과 복구

2026-10-19 / 배포 목표 4.3.3

사용자 화면의 `bootstrap.py:353 Database initialization failed`는 설치된 4.3.0.0 앱에서 발생했다. 실제 원인은 Store의 가상화 프로필 DB에서 반복된 `database disk image is malformed`이며, 읽기 전용 무결성 검사에서도 `SQLITE_CORRUPT`를 확인했다. 별도의 개발 프로필 DB는 정상이다. 두 프로필을 같은 DB로 간주하지 않았다.

손상된 DB, WAL, SHM을 `%LOCALAPPDATA%/DarkCalendarRecovery/20261019-store-db/original/`에 보존하고 원본과 SHA-256을 대조했다. 원시 DB와 복구 SQL은 저장소 밖에만 보관한다.

SQLite 공식 `.recover --ignore-freelist` 결과의 18개 기록을 스키마 16개, 캘린더 1개, 파생 인덱스 1개로 분류했다. 복구 가능한 일정 행은 0개다. 복구 후보는 무결성 `ok`, 외래키 위반 0건이다. 손상된 전체 원본과 완전한 행 대조는 불가능하므로 데이터의 완전한 복구를 단정하지 않는다.

복사본에서 현재 수정 소스와 실제 설치 4.3.0 PYZ 구현으로 DB 초기화와 캘린더 마이그레이션을 각각 두 번 실행했다. 기존 행의 원래 열에 대한 정렬 값 해시와 개수가 유지됐고 모든 실행이 성공했다. 원본 손상 DB와 후보 원본은 변경하지 않았다.

실행 중인 앱이 없는 상태와 원본 해시를 확인한 뒤 복구본을 Store 프로필에 원자적으로 적용했다. 손상 원본은 별도 사본 두 개로 보존했다. **15:42 KST 실제 설치된 Store 4.3.0.0 앱의 DB 초기화, 트레이와 백그라운드 작업 시작, Air Calendar 창의 응답을 확인했다.** 적용 후 무결성 `ok`, 외래키 위반 0건이다. 개발 프로필과 계정 설정은 변경하지 않았다.

코드에서는 SQLite 연결 설정 실패 시 아직 연결 캐시에 등록되지 않은 연결이 닫히지 않는 경계를 수정했다. `busy_timeout`, `foreign_keys`, WAL, `synchronous` 설정 실패와 정리 중 추가 오류를 검사하는 격리 회귀 11건이 통과했다. 이 코드는 손상 DB를 자동 삭제하거나 초기화하지 않는다.

증거: `artifacts/deployment/4.3.3/20261019-store-keydeck/startup-diagnosis/`. 실제 UI의 시각적 검수는 이 실행의 사용 가능한 제어 도구로 수행하지 못했다. 위 정상 기동 증거는 현재 설치된 4.3.0.0에 대한 것이며, 4.3.3의 게시·설치 여부는 별도로 확인한다.
