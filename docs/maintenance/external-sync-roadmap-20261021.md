# 외부 캘린더 추가 기능 및 개선 계획

작성일: 2026-10-21 · 상태: 계획 수립 완료 / 후속 구현 미착수

최근 연동 안정화·보안 보완을 이어가는 계획이다. 목표는 사용자가 현재 상태와 필요한 조치를 쉽게 파악하고, 대량 일정에서도 갱신 비용을 줄이며, 검증된 변경을 설치 앱까지 전달하는 것이다. 이번 작업에서는 계획 문서와 작업 색인만 작성한다.

## 현재 기준과 우선순위

2026-10-20 보안 보완은 소스와 개발 환경에 반영되어 있다. 당시 결과는 중복 제외 1,258건 통과이며, 실제 계정·설치 앱·배포 검증 완료를 뜻하지 않는다. 근거는 [보안 점검](external-sync-security-20261020.md)과 [안정화 기록](external-sync-stability-20261020.md)이다.

현재 코드에는 동기화 허브, 서비스별 연결·일시정지·수동 동기화, 문제 목록·재시도·충돌 해결, Google 진단 내보내기, ICS 자동 갱신, CalDAV ETag 캐시가 있다. 새로 만드는 기능 목록에서 제외한다.

Yahoo·Zoho·Fastmail도 현재 서비스 카탈로그와 CalDAV 프로필에 이미 포함되어 있다. 10/12 [해외 계정 확대 계획](../global-calendar-provider-expansion-plan-20261012.md)의 후보 상태를 그대로 가져오지 않고, 현재 구현의 실서비스 검증 대상으로 분류한다. 같은 서비스의 복수 계정은 별도 후속 과제다.

| 순서 | 과제 | 구분 | 사용자에게 달라지는 점 | 초기 작업 규모 |
|---|---|---|---|---|
| 1 / P0 | 설치 환경 인수 검증 | 안정성 | 재시작·오프라인 복귀·인증 만료 후에도 일정과 연결 상태 유지 | 3~5일 + 계정/배포 준비 |
| 2 / P0 | 보안 회귀·의존성 검사 자동화 | 유지보수 | 수정할 때마다 기존 보안 보호가 사라지는 것을 조기에 발견 | 1~2일 |
| 3 / P1 | 동기화 상태와 최근 처리 이력 | 추가 기능 | 마지막 확인·전체 성공·미전송·확인 필요 항목을 구분 | 3~4일 |
| 4 / P1 | 전체 서비스 통합 진단 내보내기 | 기능 확장 | 서비스별로 화면을 옮기지 않고 민감 정보 없는 진단 저장 | 2~3일 |
| 5 / P2 | ICS 갱신 효율과 재시도 개선 | 성능·안정성 | 변하지 않은 구독의 다운로드를 줄이고 실패한 구독만 적절히 재시도 | 4~6일 |
| 6 / P2 | Outlook 변경분 조회 | 성능 | 일정이 많은 계정에서 변경분 중심으로 갱신 | 5~8일 |
| 7 / P3 | 동일 서비스 다중 계정 | 추가 기능 | 개인·업무 계정을 연결 해제 없이 함께 사용 | 분리 설계 후 산정 |

기간은 개발 1명과 검토 담당이 협업한다는 가정의 초기 실작업 추정이며 확정 일정이 아니다. 실제 계정 준비, 문제 재현, 외부 심사 대기는 별도다. 인수 검증 중 데이터 손실·인증 노출 문제가 발견되면 해당 수정이 기능 개발보다 우선한다.

## 단계별 범위와 완료 기준

### P0-1. 설치 환경 인수 검증

- 기존 `build-release.bat`, SQLite 런타임 검사, `native_release_smoke.py`와 후보 검증 절차를 재사용한다. 새 빌드·검증 프로세스를 병렬로 만들지 않는다.
- 10/20 [DB 장애 기록](store-db-recurrence-20261020.md)에 남은 안전한 SQLite 런타임·최종 패키지 검증을 선행 조건으로 연결한다. 이번 계획 수립에서는 Store 서버나 현재 설치 버전을 재조회하지 않았다.
- 격리된 새 프로필·업그레이드 프로필에서 정상 종료와 재시작을 각각 두 번 확인한다. 앱 버전·패키지 해시·검증 결과를 함께 기록한다.
- 전용 테스트 계정·캘린더로 인증, 가져오기, 지원되는 생성·수정·삭제, 네트워크 단절/복구, 토큰 만료, 권한 변경, 반복·종일·서머타임을 확인한다. 네이버·ICS는 읽기 전용 기준을 유지한다.
- **완료 기준:** 중복 생성·미요청 삭제·다른 계정 쓰기·비밀값 노출 0건, 실패 후 기존 일정 유지, 서비스별 검증표와 설치판 증거 확보. 계정이 없는 서비스는 미검증으로 남기고 모의 테스트로 대체 완료하지 않는다.

### P0-2. 보안 검사 자동화

- 기존 `scripts/run_quality_gate.py`에 이번 보안 회귀 묶음을 연결하고 Windows 검증 경로를 포함한다. Linux 기본 검사와 Windows DPAPI·파일 경로·Qt 검사의 역할을 명확히 한다.
- 기존 고정 의존성 목록을 읽어 알려진 취약점 조회를 수행하고 결과·조회 시각을 남긴다. 외부 전송 대상은 공개 패키지명·버전으로 한정한다. [OSV 공식 API](https://google.github.io/osv.dev/api/)를 활용하는 방식이다.
- 보안 조회 실패는 취약점 없음으로 표시하지 않는다. 새 의존성은 호환성·악성 응답·인증 회귀를 통과한 후 고정 버전을 갱신한다. 일괄 자동 업그레이드는 하지 않는다.
- **완료 기준:** 보안 회귀를 의도적으로 깨뜨린 합성 입력에서 검사 실패, 정상 입력에서 통과, 검사 누락·네트워크 실패가 결과에 표시, 릴리스 입력과 결과의 버전 일치.

### P1-1. 동기화 상태와 최근 처리 이력

- 기존 허브 카드에 `최근 확인`, `마지막 전체 성공`, `전송 대기`, `확인 필요`를 추가한다. 현재 마지막 성공 시각·오류·재시도 대기 표시는 그대로 활용한다.
- 최근 실행 결과는 펼쳐서 보게 한다. 예: “방금 확인 · 받은 변경 3건 · 전송 1건 · 보류 1건”. 상태만 확인한 실행을 일정 반영 성공으로 오인하지 않게 한다.
- 오프라인 편집은 기존 dirty/대기열의 집계만 보여준다. 새 전송 큐를 만들지 않는다. 사용자가 일시정지한 상태와 장애로 중단된 상태를 구분한다.
- `CalendarSyncCoordinator`의 완료 경로와 서비스별 기존 결과를 공통 요약으로 변환한다. 로컬 이력은 최대 30일/100회 중 먼저 도달하는 한도로 제안한다. 일정 제목·본문·URL·토큰은 저장하지 않는다.
- **완료 기준:** 부분 성공·취소·재시도 대기·재시작·계정 전환에서 시각과 건수가 정확하며, 중복 signal이 이력을 중복 생성하지 않고, 표시 갱신이 네트워크 동기화를 추가로 실행하지 않는다.

### P1-2. 전체 서비스 통합 진단 내보내기

- 허브의 기존 문제 화면에서 모든 연결 서비스의 상태·안전한 오류 종류·대기 건수·앱/의존성 버전을 한 파일로 저장한다. 저장 전 포함 항목을 보여준다.
- Google의 `_export_diagnostics_report()` 수집·정규화 로직을 공통 수집 경로로 옮기고 기존 버튼도 같은 경로를 사용한다. Google 전용 구현을 복사해 서비스별 exporter를 만들지 않는다.
- 화면 상태와 DB 집계를 읽으며 원격 요청·재인증·자동 업로드를 실행하지 않는다. 계정 주소·캘린더 이름·일정 내용·원문 로그·인증 URL을 제외한다.
- **완료 기준:** 모든 서비스에서 동일한 필드 의미, 연결하지 않은 서비스 처리, DB 조회 실패의 안전한 표시, 합성 비밀값 0건, 기존 Google 버튼과 허브 버튼의 출력 일치.

### P2-1. ICS 갱신 효율과 재시도 개선

- 기존 `subscription_http.py`와 `fetch_and_sync()`에 조건부 요청을 연결한다. 서버가 제공하는 ETag/Last-Modified를 활용하고 지원하지 않으면 현재 전체 다운로드로 동작한다. HTTP 304는 본문 없는 변경 없음 응답이므로 빈 캘린더로 처리하지 않는다. [HTTP 조건부 요청·304 규칙](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5)
- 검증된 원문과 검증자를 함께 캐시하고, 304에서도 기존 `_snapshot()`으로 현재 시각·시간대 기준의 반복 일정을 다시 전개한다. 본문이 같아도 과거 120일~미래 400일 범위는 이동하므로 DB 행만 재사용하지 않는다. 캐시가 없거나 손상되면 조건 없이 전체 수신한다.
- 원문 캐시는 사용자 전용 저장 경로에 두고 현재 피드당 8MiB 제한과 전체 용량 상한을 적용한다. 구독 삭제 시 정리하며 진단 보고서·로그·배포물에 포함하지 않는다. 캐시를 별도의 일정 원본이나 전송 큐로 사용하지 않는다.
- URL 변경·삭제·재등록 시 검증자와 성공 기준을 함께 무효화한다. 검증자 저장은 정상 스냅샷 반영과 일관되게 처리한다. 실패한 본문을 새 기준으로 저장하지 않는다.
- 구독별 재시도 예정 시각을 기존 coordinator의 자동 갱신 판단에 연결한다. 기존 HTTP Retry-After 해석을 재사용하고 429/일시적 네트워크 오류와 인증·주소 오류를 구분한다. 구독마다 새 타이머를 만들지 않는다.
- **완료 기준:** 지원 서버의 동일 피드 두 번째 확인에서 본문 수신 0바이트, 일정 변경·삭제 0건. 날짜 이동·시간대 변경·재시작·304 오응답·캐시 저장 실패에서도 최신 전개 범위와 기존 데이터 보존. 한 실패 구독이 정상 구독의 갱신을 막지 않음.

### P2-2. Outlook 변경분 조회

- 현재 `GraphClient.events()`의 calendarView 전체 조회를 보완한다. 캘린더별·조회 기간별로 변경 추적 상태를 관리하고 모든 페이지가 반영된 후 마지막 deltaLink를 저장한다. [Microsoft의 calendarView delta 문서](https://learn.microsoft.com/en-us/graph/delta-query-events)
- 공통 엔진의 `events()`는 현재 완전한 스냅샷을 기대한다. 변경분 목록을 그대로 넘기지 않는다. 우선 어댑터 내부 캐시에서 완전한 스냅샷을 재구성해 기존 엔진·충돌·삭제 판단을 보존하는 설계를 검증한다.
- 토큰 만료·기간 변경·캐시 불일치·권한 변경은 기존 전체 조회로 복구한다. deltaLink에도 현재 Graph 호스트·크기·시간 제한을 적용하며 원문 토큰을 진단에 남기지 않는다.
- **완료 기준:** 전체 조회 기준과 최종 DB 결과가 동일하고, 반복 회차·삭제·페이지 중단·동시 로컬 수정·재시작을 통과하며, 동일 데이터셋에서 수신량·호출 횟수가 감소한다. 착수 전 기준 측정값을 남기고 임의의 속도 개선 수치를 약속하지 않는다.

### P3. 확장 후보

- **동일 서비스 다중 계정:** 먼저 계정/캘린더/인증 저장소/삭제 대기/동시 실행의 identity 계약을 확정한다. 기존 계정별 DB·암호화 저장 기반을 재사용하고 현재 단일 계정 설정은 원자적으로 이관한다. 일부 화면에 계정 선택만 추가하는 방식으로 진행하지 않는다.
- **CalDAV sync-token:** 기존 ETag 목록·변경 본문 캐시로 성능을 측정한 뒤 추가 가치가 있을 때 진행한다. [RFC 6578](https://www.rfc-editor.org/rfc/rfc6578.html) 지원 여부를 서비스별로 확인하고 미지원·만료 시 기존 경로를 유지한다.
- 임의 CalDAV 서버 입력, 서비스 간 자동 복제, 반복 일정의 일괄 편집, 자동 충돌 병합은 첫 두 단계에서 제외한다. 인증정보 전달 범위·삭제 의미·소유권 설계가 필요하므로 후속 수요와 위험을 따로 검토한다.

## 중복 구현·기존 처리 충돌 방지 기준

| 책임 | 재사용할 원본 | 금지할 중복 |
|---|---|---|
| 수동·자동 실행/상태 | `calendar_sync_coordinator.py`, 기존 서비스 컨트롤러 | 별도 동기화 타이머·서비스 실행기 |
| 일정 저장·충돌·삭제 | Google 엔진 / 공통 `calendar_sync/engine.py`·repository | UI가 직접 원격 쓰기, 두 번째 삭제·전송 큐 |
| 진단·오류 표시 | `calendar_sync/status.py`, `sync_feedback.py`, 공통 로그 정규화 | 서비스별 원문 예외 복사·중복 exporter |
| HTTP/주소/파싱 보호 | 기존 HTTP helper·서비스별 URL 검증·공통 iCalendar parser | 검증을 우회하는 새 HTTP client나 파서 |
| 서비스 추가 | `calendar_provider_catalog.py`, CalDAV profiles | 화면마다 다른 서비스 목록·권한 기준 |
| 빌드·버전·배포 | 기존 통합 빌드·검사·변경 기록 | 별도 배포 스크립트·수정 횟수에 따른 버전 증가 |

새 상태는 기존 초기화 경로에, 새 저장 필드는 기존 마이그레이션 체계에 넣는다. 구현 전 호출부·실패 시 롤백·중단 후 재개·계정 분리·기존 테스트를 함께 확인한다. 새 공통 함수를 만들면 기존 호출부를 함께 연결하고 같은 책임의 옛 구현을 남기지 않는다.

## 실행 순서와 역할

1. **첫 묶음:** P0 인수 환경 준비·보안 자동 검사. 실제 계정 준비가 늦어지면 독립적인 CI 작업부터 진행하되 미검증 서비스의 출시 완료를 선언하지 않는다.
2. **두 번째 묶음:** P1 상태/이력 → 같은 공통 상태를 이용하는 통합 진단. 이 두 항목을 첫 사용자 기능 후보로 잡는다.
3. **세 번째 묶음:** ICS 개선 → 측정·인수 → Outlook 변경분 조회. 서로 다른 스냅샷 의미를 한 번에 바꾸지 않는다.
4. **확장 판단:** 위 검증 결과와 실제 복수 계정 수요를 확인한 뒤 P3 설계에 착수한다.

개발 담당은 공통 계약·구현·회귀 근거를, 검토 담당은 재현·중복 책임·보안·릴리스 증거를 확인한다. 제품 담당은 초기 범위와 인수 결과를 판단하고 필요한 테스트 계정·서비스 접근 조건을 준비한다. 계정 인증은 정상 로그인 흐름으로 진행하며 비밀번호를 계획 문서나 채팅에 기록하지 않는다.

이 계획은 기존 정기 유지보수 일정과 배포 계획을 변경하지 않는다. 문서 변경만 이력에 등록하고 제품 버전은 4.6.9를 유지한다. 실제 구현과 배포 범위가 정해지면 해당 규칙에 따라 별도로 기록한다.
