# 버전 부여와 변경 등록

사용자 확정 규칙(2026-10-15): `첫째.둘째.셋째`, 각 자리 0~9. 일반적인 Semantic Versioning의 호환성 의미를 적용하지 않는다.

| 자리 | 증가 조건 | 예시 |
|---|---|---|
| 셋째 | 개별 기능 수정·오류 정정·UI 개선 1건. 스케줄러 수정 포함 | 3.8.1 → 3.8.2 |
| 둘째 | 모듈의 추가·교체·구조/계약 변경 1건, 또는 새 Store 업로드를 위한 릴리스 준비 | 3.8.4 → 3.9.0 |
| 첫째 | 둘째 자리 9에서 올림 발생 | 3.9.4 → 4.0.0 |

셋째 자리 9 다음은 둘째 자리 +1·셋째 자리 0이다. 둘째 자리를 올릴 때 셋째 자리는 0으로 초기화한다. 한 변경이 여러 조건에 해당하면 높은 단계 한 번만 적용한다. 모듈 변경과 이후 별개의 Store 릴리스 준비는 서로 다른 이벤트다. 세 자리 모두 9인 경우 임의로 두 자리 숫자를 만들지 않고 새 규칙이 필요함을 알린다. MSIX/PE는 같은 버전 뒤 `.0`을 붙인다.

## 등록 단위

파일 저장 횟수가 아닌 독립된 수정 작업 1건을 기준으로 한다. 관련 파일 여러 개를 함께 고쳤으면 한 이벤트다. 하나의 실행에서 독립 오류 세 건을 고쳤으면 세 이벤트다. 검토만 한 경우, 문서·검사 로그만 갱신한 경우, 단순 재실행·빌드·업로드 재시도에는 올리지 않는다. 버전 부여 자체는 검증 통과·게시·설치 완료를 의미하지 않는다.

모든 코딩/정기 수정은 작업을 마칠 때 다음 명령을 실행한다. 이벤트 ID는 작업/릴리스에 대해 고정하고 재시도 시 재사용한다. 변경 내용을 바꿨다면 기존 ID를 재사용하지 않고 새 수정 이벤트로 등록한다.

```powershell
.venv/Scripts/python.exe scripts/manage_version.py record --kind change --event-id <고정-작업-ID> --summary "변경 내용" --files calendar_app/변경파일.py tests/관련검사.py
.venv/Scripts/python.exe scripts/manage_version.py record --kind module --event-id <고정-모듈작업-ID> --summary "모듈 변경 내용" --files calendar_app/변경모듈.py
```

`module`은 단순히 Python 파일을 수정했다는 뜻이 아니다. 기존 함수의 버그 수정은 `change`다. 모듈 추가·교체 또는 외부 계약·구조 변경에 사용한다.

스케줄러는 개별 수정마다 등록한 후 실행 종료 직전 `scan`으로 누락을 확인한다. `run.bat`도 앱 시작 전에 `scan`을 실행한다. 미등록 실행 입력이 있으면 그 변경 묶음을 셋째 자리 한 번으로 등록한다. 프로그램 실행 중의 매 키 입력·저장마다 감시하는 백그라운드 프로세스는 없다. 개발자가 수동 편집한 내용을 반영하는 시점은 명시적 등록 또는 다음 `run.bat` 실행이다. 버전 처리 실패 시 옛 번호로 앱을 시작하지 않는다.

```powershell
.venv/Scripts/python.exe scripts/manage_version.py scan
.venv/Scripts/python.exe scripts/manage_version.py status
```

## Store 준비와 재시도

새 Store 업로드는 패키지를 빌드하기 **전에** `record --kind store --event-id store-<주기/릴리스-ID> --summary "Store 릴리스 준비"`로 둘째 자리를 올린다. 출력된 버전으로 앱·Git 태그·MSIX를 맞추고, 이미 만들어진 패키지의 이름이나 메타데이터만 사후 변경하지 않는다. 단순 업로드 재시도는 같은 ID와 검증된 패키지를 사용한다. 같은 입력의 Store 이벤트는 다른 ID로 재호출해도 증가하지 않는다. 준비 후 코드가 바뀌면 별도의 수정으로 등록하고 새 릴리스 입력으로 다시 검증한다.

`build-release.bat`는 현재 등록 버전과 다른 번호를 직접 지정하면 중단한다. 빌드 자체는 버전을 증가시키지 않는다. Store 초안/심사 중 버전을 개발 번호로 덮어쓰지 않는다.

## 사용자가 명시한 미공개 버전 교정

사용자가 배포 버전을 명시해 미공개 예약 번호를 정정하도록 지시한 경우에만 `override`를 사용한다. 기존 `change`/`module`/`store` 기록은 보존하고 교정 이벤트를 추가한다. 대상 버전과 실제 공개 버전은 세 자리 각 0~9이며, 대상은 확인된 실제 공개 버전보다 높아야 한다. `--published-version`에는 빌드가 미리 바꾼 공개 예정 메타데이터 대신 실제 게시 증거로 확인한 번호를 넣는다. 게시된 패키지의 버전을 낮추거나 기존 파일 이름만 바꾸는 용도로 사용하지 않는다.

```powershell
.venv/Scripts/python.exe scripts/manage_version.py override --version 4.3.3 --published-version 4.3.0 --event-id user-release-4.3.3 --summary "사용자 명시 요청에 따른 미공개 배포 버전 교정"
```

같은 교정 재시도에는 같은 ID·대상·공개 기준·실행 입력을 사용한다. 교정은 현재 전체 실행 입력을 등록하므로 별도 자동 증가나 새 `store` 등록 없이 해당 번호로 다시 검증·빌드한다. 이후 별개의 변경과 새 릴리스 준비에는 기본 자동 증가 규칙을 그대로 적용한다.

## 기록과 복구

- 원본 이력: 프로젝트 `version-history.json`의 이전/새 버전, 이벤트 ID, 종류, KST 일시, 내용, 파일 해시.
- 보기용 이력: [버전 변경 이력](../docs/maintenance/version-history.md).
- 개발 버전: `app_metadata.py`, `pyproject.toml`, `AppxManifest.xml`, `version_info.txt`를 함께 갱신한다. 개발 변경의 채널은 `Dev`다.
- 마지막 공개 버전: `APP_PUBLISHED_VERSION/DATE`와 홈페이지에는 실제 공개된 버전을 유지한다. 릴리스 준비 빌드는 공개용 메타데이터도 맞추며, 실제 게시 성공은 별도 증거로 확인한다.
- 중단 복구: `.versioning/`의 실제 배타적 잠금·원자 교체·저널을 사용한다. 새 사용자 편집이 끼어 있으면 덮어쓰지 않고 중단한다. 해당 폴더는 로컬 실행 상태이며 Git에서 제외한다. 이력 JSON/MD는 소스와 함께 릴리스 커밋한다.

개인 DB·토큰·사용자 설정은 입력 해시나 버전 증가 대상으로 삼지 않는다. 자동 실행 입력 검사는 코드·리소스·번역·의존성·빌드/실행 스크립트의 추가·변경·삭제를 포함하며, 버전/날짜/채널만 변경된 경우와 줄 끝 차이로는 반복 증가하지 않는다.
